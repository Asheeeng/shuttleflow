# V0.2 产品化与规则辅助调度

## 增量升级与数据保护

沿用原Vue/Spring Boot/JPA/MySQL模块化单体和认证、候车、到站、ETA接口。V1迁移及原30个JUnit、32条HTTP断言、2条浏览器流程保持不变。V2新增当日车辆、下客计划、调度任务三表，V3增加人工处理审计字段。Flyway在现有库原位迁移，不删除V0.1业务表；本次升级前另存源码及数据库备份在`.runtime/backups`，不会进入源码归档。

高峰初始化是仅demo且非prod/production环境的明确确认操作，会重置演示运营记录；日常启动不会重置数据。基础账号ID保留。原有“重置演示数据”仍可复现V0.1，额外高峰车辆在基础模式置为不可用。

## 三端体验

乘客以选站、ETA和候车动作为主，线路示意明确不是实时定位；展示司机最近报站及载客状态。底部“一键候车”直接调用原创建接口，状态同步后滚动到当前请求；已存在请求时底部入口转到“我的候车”。取消、上车、超时及重复防护继续由原状态机负责。

司机突出车辆、下一站、人数和安全停靠确认，新增调度通知及下客计划。任务接收要核实当前车内人数和驻车位置，拒绝必须说明理由；运行中仍依次报站，不允许派单绕过原容量与站序校验。预计下客计划不写入实际人数。支援站完成只结束调度任务，不会自动将候车乘客标记上车。

管理员显示四项关键统计、站点需求/预计容量/缺口、逐车计算详情、可解释候选车、任务和当日状态。全部读取实际后端接口，10秒轮询，并保留错误、空状态、加载和反馈。关键危险动作先明确确认；派单后需司机应答才进入运行运力。

## 当日车辆

`vehicle_day`按Asia/Shanghai的服务日期保存，vehicle_id+service_date唯一，driver_id+service_date唯一（允许NULL）。状态RUNNING、STANDBY、UNAVAILABLE；记录绑定司机、线路、驻车站、准备秒数、状态说明和更新时间。

跨日不会自动沿用昨日RUNNING，须重新确认当日可用性。升级当天只接纳同日已存在的人工报站任务。不可用车辆不参与候选；有待接单或执行中任务时禁止直接调整状态。标为不可用必须填写原因；恢复运行要求仍有效的位置报告，过期车辆应通过司机接单确认重新启动。暂不提供任意司机/车辆绑定CRUD，演示使用预置绑定。

## 运力与预警

每次从数据库读取尚未过期的WAITING请求，人数为party_size-boarded_count；只纳入当日RUNNING、原任务RUNNING、载客人数已确认且上报未过15分钟的车辆。排除项在管理端明细解释。

预测窗口默认10分钟，阈值为缺口≥5人。每辆车从最近站点开始，按历史站间耗时生成未来到站事件；所有车辆事件按预计时刻、车辆ID和站序稳定排序。在每个事件中：

1. 从车内人数扣除该站人工计划下客人数（不能超出现有车内人数）。
2. 可用座位=额定容量-下客后人数。
3. 分配上客=min(该站尚未分配需求, 可用座位)。
4. 更新本车后续载客量及本站剩余需求。

缺口=有效需求-分配的预计上客人数。这样同一站多车共享同一需求池，上游已占用座位不会在下游重复计入，下客释放的容量在上客前计算，所有预测人数也不能超载。

实际人数仅由司机到站事务修改，原Service使用同一先下客后上客公式并拒绝非法人数；预测不代替实际记录。没有下客计划时按0人预计下客，避免无依据高估座位。计划必须有来源且司机填写的后续总计划人数不能超过最近确认的车内人数。到站后消费该站计划，实际上下客可与原计划不同，以实际确认值为准。

## 建议、并发与任务闭环

候选必须为当日STANDBY、具备有效预置司机/任务/线路/驻车站、人数已确认、未被其他未结束任务占用；目标须位于驻车站下游，准备时间+同向累计ETA须在10分钟窗口内。最近10分钟同目标的拒绝/超时车辆暂不再次推荐。候选的目标站预计余座使用同一多车/多站预测器，扣除它途中可能承接的上游需求，再按ETA升序、余座降序、车辆ID排序。

管理员确认时重新计算缺口与候选资格。运行车不能当待命车重复派发；PENDING仅作为待接单预留容量，仍不算已运行运力。已被待接单覆盖的缺口不再生成重复建议。MySQL连接使用READ_COMMITTED，配合线路行锁串行化同线路派单、车辆行锁保护状态、active_vehicle_id可空唯一约束兜底；避免RR旧快照令不同车辆重复占同一缺口。

| 当前状态 | 动作/条件 | 结果 |
| --- | --- | --- |
| 无任务 | 管理员确认有效建议 | PENDING，占用车辆，默认2分钟应答期限 |
| PENDING | 指定司机确认驻车位置、核实车内人数并接受 | ACCEPTED，车辆和任务变RUNNING，基于实际出发时刻重算预计到达；满载不允许接受增援任务 |
| PENDING | 指定司机填写理由拒绝 | REJECTED，释放占位，升级管理员 |
| PENDING | 达到deadline_at | TIMED_OUT，释放占位，升级管理员，车辆不启动 |
| PENDING | 管理员撤回 | CANCELLED，释放占位 |
| ACCEPTED | 按线路到达支援站并报站 | COMPLETED，原载客量与到站记录事务同时完成任务 |
| ACCEPTED | 预计到达后5分钟仍无支援站上报 | TIMED_OUT并升级；保留实际车辆运行状态，不假装停运 |
| REJECTED/TIMED_OUT且待处理 | 管理员确认顺延 | 重算当前缺口，给下一候选车新建PENDING，保留previous_task_id链；旧任务不复活 |
| 升级任务且无法或无需顺延 | 管理员记录人工处理结果 | 保留原终态，记录resolved_by/resolved_at/resolution_note，关闭待处理标记 |

每5秒检查应答及执行超时，查询调度板和司机通知时也补做检查。迟到接受不能启动已结束任务。无候选或缺口已经消失会给出明确提示，可人工标记处理，不伪造已派车结果。

## 课间高峰场景与来源

管理员点击“初始化课间高峰”，确认后调用仅demo环境的`POST /admin/demo/peak`，confirmation=INIT PEAK。数据全部为本地确定性夹具，并非贵州大学真实运营数据：

| 项目 | 模拟值 |
| --- | --- |
| DEMO-01 / driver | A站，18/20人，运行中；B计划下1人、C计划下4人 |
| DEMO-03 / driver3 | B站，16/20人，运行中；C计划下3人 |
| DEMO-02 / driver2 | A站待命，0/20人，准备1分钟 |
| DEMO-04 / driver4 | A站待命，0/20人，准备2分钟 |
| DEMO-05 | 演示检修，不可用，不参与推荐 |
| B站候车 | 一组2人有效请求 |
| C站候车 | 两组20人+10人有效请求 |
| 历史站间耗时 | A→B 4分钟、B→C 3分钟、C→D 5分钟 |

在初始化当下：DEMO-03约3分钟到C，可释放7座；DEMO-01约4分钟到B，18-1+2=19人，约7分钟到C，下客4人后释放5座；C合计12座、缺口18人。建议DEMO-02准备1分钟+7分钟路程，预计8分钟到C；DEMO-04约9分钟。既有运行车已承接B站需求，因此此夹具两辆备车预计在C可用20座。其他上游需求变化时会重新计算，不能固定套用20座。

演示角色统一密码Demo123456!，数据库保存BCrypt哈希：passenger、admin、driver、driver2、driver3、driver4。额外司机在初始化演示数据时创建，非生产账号体系。乘客默认C→D可提交自己的真实演示请求，使需求增加；截图中的计数取自实际数据库而非UI写死。

## 新API（均保留原接口）

统一响应、Session、CSRF和角色规则沿用原API文档。

| 方法/路径（/api前缀） | 权限 | 用途/主要字段 |
| --- | --- | --- |
| GET /passenger/service?routeId= | PASSENGER | 线路运行车辆、站点需求与运力状态 |
| GET /admin/dispatch-board | ADMIN | alerts、suggestions（含候选解释）、tasks、serverTime |
| GET /admin/fleet | ADMIN | 当日出勤、准备时间、绑定、驻车站 |

| POST /admin/dispatches/{id}/cancel | ADMIN | 撤回尚未接受的任务 |
| POST /admin/dispatches/{id}/resolve | ADMIN | note；人工处理审计，终态保持 |
| GET /driver/dispatches | DRIVER | 本司机通知及历史，不可读取其他司机任务 |

## 复现与边界

启动方式沿用根README。先停止jar再`mvn package`，用`./scripts/backend.sh --jar`启动`campus-shuttle-0.2.0.jar`。后台、数据库与前端启动后，顺序执行原HTTP、V0.2 HTTP（带--check-timeout真实等待约2分钟）、浏览器测试，避免多个脚本同时重置同一库。

调度为规则辅助，非GPS跟踪、机器学习预测或无人确认的自动派单。预计座位取决于人工数据，人数未确认/报站过期会排除；候车TTL10分钟，不推断未来需求续期。单向线路不自动折返，同驻车站的即时支援不作为“未来到站”推荐。任务完成表示到达支援站，乘客仍自己确认上车。当前绑定预置、历史列表未分页、轮询非推送、未做生产部署与压测。

下一阶段可增加绑定与班次管理、历史站间采样、分时需求留存模型、位置置信度、前端按需组件拆包、调度策略效果校准。当前全量Element Plus构建首包约1.15MB（gzip约381KB），本地演示已验证，公网部署前宜拆分路由与组件。
