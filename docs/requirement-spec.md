## 1. 项目背景

### 1.1 问题域

贵州大学校园面积较大，师生跨校区、跨教学楼出行依赖校园摆渡车。现有摆渡车运营存在以下客观条件：

- **三条固定线路**：
  - 1 号线：去向 9 站 / 回向 13 站
  - 2 号线：去向 9 站 / 回向 13 站
  - 3 号线：去向 10 站 / 回向 14 站
- **车辆编组**：共 12 辆车，每辆额定容量 13 人
  - 1～4 号车 → 1 号线
  - 5～8 号车 → 2 号线
  - 9～12 号车 → 3 号线
- **运营场景**：课间 10 分钟、就餐高峰、雨雪天气、大型活动散场等场景下客流呈突发性与方向性聚集。

### 1.2 三个不假设（设计前提）

本系统在需求层面明确放弃以下三类"理想化假设"，转而以多源观测融合与算法鲁棒性来应对不确定性：

| 编号 | 不假设内容 | 对应工程对策 |
|------|------------|--------------|
| H1 | 不假设乘客会扫码 | 多源观测：司机到站点击 + 人工观测 + 扫码签到三方融合，任一来源缺失仍可估计 |
| H2 | 不假设司机能数清 | 车内人数由守恒方程递推 + 卡尔曼滤波修正，司机点击仅作事件触发而非精确计数 |
| H3 | 不假设课表 = 客流 | 课表仅作先验基线，实际客流由实时观测驱动，CUSUM 检测课表偏离并触发再调度 |

### 1.3 技术栈

| 层 | 技术 |
|----|------|
| 后端 | Spring Boot 2.7.18 + MyBatis-Plus + MySQL 8.0 + Redis + WebSocket |
| 前端 | Vue3（Composition API） |
| AI 服务 | Python + FastAPI |
| 通信 | REST + WebSocket（实时推送） |

## 2. 五个痛点

| 编号 | 痛点 | 现状描述 | 量化影响 |
|------|------|----------|----------|
| P1 | 高峰突发客流 | 课间 10 分钟内单站聚集可达 80+ 人，固定班次无法响应 | 等待时长 > 15 分钟，滞留率 > 40% |
| P2 | 多车同时到站 | 2～3 辆车同时抵达同一站点，运力浪费且乘客选择混乱 | 同站并发到站概率 18%，空驶率上升 12% |
| P3 | 实时监测缺失 | 调度员无法实时掌握各站客流与各车载载率 | 调度响应延迟 > 5 分钟 |
| P4 | 司机不知车内人数 | 司机无法准确掌握当前载客数，难以判断是否继续接客 | 超载风险 + 拒载误判 |
| P5 | 车辆是否运行不明 | 管理端无法确认车辆是否在线、是否在执行任务 | 空车派单、任务悬空 |

## 3. 角色与用例

### 3.1 乘客（Passenger）

```
用例 P-01：扫码签到上报
  前置：乘客到达站点，站点张贴二维码
  主流程：扫码 → 选择去向 → 提交 → 系统融合入队 → 返回排队序号与 ETA
  备选：网络异常 → 本地缓存 → 弱网轮询重试（5 秒间隔）

用例 P-02：查询 ETA
  前置：已签到或仅查询
  主流程：输入站点 + 去向 → 返回预计等待时长、预计车辆编号、队列前方人数

用例 P-03：取消签到
  前置：已签到未上车
  主流程：取消 → 系统从队列移除 → 通知调度
```

### 3.2 司机（Driver）

```
用例 D-01：登录与设置当日运行
  主流程：工号登录 → 选择线路 + 班次方向 → 系统登记车辆状态为 running

用例 D-02：到站三次点击
  说明：到站 / 上车 / 下车 三类事件分别点击，不要求精确计数
  主流程：
    - 到站点击：触发 arrive 事件，系统记录站点与时间
    - 上车点击 n 次：触发 board 事件，n 为本站上车人数
    - 下车点击 m 次：触发 alight 事件，m 为本站下车人数

用例 D-03：人数校准
  主流程：司机目测输入当前车内人数 → 系统以卡尔曼滤波融合修正

用例 D-04：接单 / 拒单
  主流程：收到调度任务 → 接受（assigned→accepted→executing）或拒绝（assigned→rejected→escalated）
```

### 3.3 管理员（Admin）

```
用例 A-01：查看调度大屏
  主流程：实时查看三线路各站客流、各车载载率、预警事件

用例 A-02：人工观测上报
  主流程：选择站点 → 输入目测人数 → 系统融合入观测序列

用例 A-03：创建调度任务
  主流程：选择车辆 + 目标站点 + 任务类型 → 系统评分排序 → 派发

用例 A-04：查看预警与事件流水
  主流程：查看 CUSUM 突变告警、满载预警、任务超时事件

用例 A-05：仿真台操作
  主流程：消融实验 / 课表预测 / 多车分配演示 / 卡尔曼融合演示
```

## 4. 功能需求

### 4.1 FR-1 多源客流上报与融合

**描述**：支持乘客扫码、司机到站点击、管理员人工观测三种来源的客流上报，系统对同一站点同一时段的多源观测进行融合，输出该站该去向的估计客流值。

**输入源**：
- 乘客扫码签到（checkin）
- 司机到站事件（arrive）+ 上车/下车计数（board/alight）
- 管理员人工观测（observation）

**融合规则**：
- 同站同去向同时间窗（Δt = 30s）内多源观测取加权融合
- 权重：扫码 0.5 + 司机点击 0.3 + 人工观测 0.2（缺源自动归一化）
- 融合后写入站点客流快照表

**验收标准**：
- 任一单源缺失时系统仍能输出估计值
- 三源同时上报时融合值 = 0.5×扫码 + 0.3×司机 + 0.2×人工

### 4.2 FR-2 实时监测与预警

**描述**：对三线路所有站点的客流、所有车辆的载载率进行秒级监测，触发预警并推送。

**预警类型**：
- 站点聚集预警：站点估计客流 > 阈值（默认 20 人）
- 车辆满载预警：载载率 ≥ 95% 持续 10 秒（滞回触发，解除阈值 85%）
- 车辆离线预警：车辆心跳超时 > 60 秒
- 任务超时预警：任务 assigned 后 120 秒未 accepted

**推送方式**：WebSocket 实时推送至管理端大屏

### 4.3 FR-3 短时预测与突变检测

**描述**：基于历史客流与实时观测，对未来 15 分钟各站客流进行预测，并检测客流突变。

**预测算法**：课表先验 + 卡尔曼滤波实时修正
- 先验 μ₀：由课表与历史均值生成
- 观测 z：实时融合客流
- 修正：x̂ = x̂⁻ + K(z − x̂⁻)，K = P/(P+R)

**突变检测**：CUSUM 算法
- Sₜ = max{0, Sₜ₋₁ + (xₜ − μ₀ − k)}
- 当 Sₜ > h（阈值默认 15）触发突变告警

### 4.4 FR-4 多车协同分配

**描述**：当某站点出现客流聚集或多车同时到站时，系统以最小费用流模型对多车进行协同分配，避免运力浪费。

**模型**：
- 节点：当前可用车辆集合 + 需求站点集合 + 超级源汇
- 边：车辆→站点，费用 = ETA + 负载惩罚 + 空驶距离
- 求解：最小费用最大流，输出车→站分配方案

**约束**：
- 已满载车辆不参与分配
- 同一线路车辆优先分配至同线路站点

### 4.5 FR-5 车辆运行与任务派发

**描述**：管理车辆运行状态，基于评分模型向车辆派发调度任务。

**车辆状态**：offline / idle / running / full / maintenance

**任务派发评分**：
```
score = ETA_norm × 0.4 + loadRate_norm × 0.4 + status_norm × 0.2
```
- ETA_norm：预计到达时间归一化（越短分越高）
- loadRate_norm：当前载载率归一化（越低分越高）
- status_norm：车辆状态归一化（idle > running > others）

**派发流程**：候选车辆评分排序 → 取 top1 → 创建任务（pending→assigned）→ 推送司机端

### 4.6 FR-6 运营分析与仿真

**描述**：提供运营数据分析与算法仿真台，支持消融实验对比不同调度策略效果。

**分析功能**：
- 日/周客流统计
- 各线路满载率、平均等待时长
- 任务完成率、超时率

**仿真功能**：
- 消融实验：4 策略对比（仅课表 / 课表+卡尔曼 / 课表+卡尔曼+CUSUM / 全策略）
- CUSUM 状态可视化
- 课表预测对比
- 多车分配演示
- 卡尔曼融合演示

## 5. 非功能需求

| 编号 | 类别 | 指标 | 说明 |
|------|------|------|------|
| NFR-1 | 时延 | 端到端 ≤ 2 秒 | 从观测上报到大屏更新全链路时延 |
| NFR-2 | 可靠性 | QoS1 幂等 | 关键上报消息至少一次送达 + 幂等去重（基于事件 ID） |
| NFR-3 | 弱网适应 | 5 秒轮询 | 弱网/断线时前端 5 秒间隔轮询重试 |
| NFR-4 | 离线缓存 | 断网缓存 2 小时 | 司机端断网时本地缓存事件，恢复后批量补传 |
| NFR-5 | 满载滞回 | ≥95% 触发，10 秒确认 | 载载率 ≥95% 持续 10 秒触发满载预警，≤85% 解除 |
| NFR-6 | 可用性 | 系统可用率 ≥ 99% | 7×12 运营时段内 |
| NFR-7 | 并发 | 支持 200 并发连接 | 含 WebSocket 长连接 |
| NFR-8 | 安全 | 角色鉴权 + 接口权限 | JWT + RBAC |

## 6. 约束条件

1. **硬件约束**：车辆无 GPS、无称重、无自动计数，仅司机手机 App 作为终端
2. **网络约束**：校园部分区域信号弱，需支持弱网与断网恢复
3. **成本约束**：不增设额外硬件，纯软件方案
4. **线路约束**：三线路固定，站点与车辆编组在部署时配置，运行期不变
5. **容量约束**：单车额定 13 人，超载不予发车
6. **课程约束**：需体现软件工程完整生命周期，含需求/设计/编码/测试/文档

## 7. 术语表

| 术语 | 定义 |
|------|------|
| 去向 | 线路正向方向（站点序号递增） |
| 回向 | 线路反向方向（站点序号递减） |
| 载载率 | 当前车内人数 / 额定容量(13) |
| ETA | 预计到达时间（Estimated Time of Arrival） |
| 守恒方程 | Lᵢ(t+Δt) = max{0, Lᵢ(t) + Aᵢ − Bᵢ}，车内人数递推 |
| CUSUM | 累积和突变检测算法 |
| 滞回 | 触发阈值与解除阈值不同，避免抖动 |
| 消融实验 | 逐项移除算法组件，对比效果下降量 |
