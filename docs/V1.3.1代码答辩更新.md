# ShuttleFlow V1.3.1 代码答辩更新

这份更新与原中期手册配合使用。手册保留在 `v1.3.0-midterm` 时代的代码链接，当前部署源码固定为 [5540681](https://github.com/Asheeeng/shuttleflow/tree/5540681e68499449179e95cdb5fa5be045acb84e)。系统图、逻辑 ER 图见 [当前设计](design-doc.md)。

## 必须掌握

1. **两域名是否代表两套服务？** 两个 Nginx vhost 都代理到同一个 Java。MySQL 和 Redis 单实例，业务只写正式库。旧实验库原样保留供只读查询，没有另跑一套正式后端。
2. **业务和算法实验怎么隔离？** 正式事件写 MySQL、向 Redis 记摘要、向 WebSocket 广播；实验没有业务 HTTP 写客户端、没有数据库或 Redis 连接，也没有在线 AI 令牌，只读配置、在内存推进、将结果写独立 JSON。
3. **原来 HTTP 仿真怎么用？** 它是真业务接口的集成测试工具，使用临时测试库和独立组件，能测试真实事务。生产被关闭；不能拿历史仿真的通过率当作 V1.3.1 策略实验结果。
4. **前端为何不用共享 Basic Auth？** 登录成功建立角色会话，匿名可读公开线路，司机和管理接口由服务器验证身份。写请求仍校验 CSRF，受限地址仅通过回环监听。
5. **如何做到实时且不越权？** WebSocket 握手校验 Origin 和会话，按角色/车辆过滤，每 25 秒发 Ping，并复核会话是否仍有效；实验台的运行结果单独轮询，不通过生产 WebSocket 推送。
6. **这是否证明改造后实际客流等待时间下降？** 未采集真实校园客流。当前同一条模拟序列为 100 人、4 车，固定班次与阈值组平均 649.9 秒，智能组 417.8 秒，三组均 65 人上车、35 人取消。只统计已上车者，不能外推到线上，更不能宣称全局最优。
