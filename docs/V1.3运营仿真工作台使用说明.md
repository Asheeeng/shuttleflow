# ShuttleFlow V1.3 运营仿真工作台

> 以下说明适用于临时 HTTP 集成测试。正式工作台使用内存虚拟乘客和司机，不能为真实测试账号生成模拟车辆；当前入口和实验口径见 [V1.3.1 正式部署验收](deploy/V1.3.1正式部署验收报告.md)。

## 启动与加入

在 V1.3 工作区执行 `python3 simulation/runtime.py start --run-dir /private/tmp/shuttleflow-demo-20261118`。运行器在本机测试 MySQL 3308 创建专属数据库和受限应用账号，另起 Redis 16379、FastAPI 18000、运营进程 18001 和 Java 18080。新建运行目录应换一个尚未存在的名字。

访问 [本机仿真工作台](http://127.0.0.1:18080/login.html?role=admin&next=simulation.html)。管理员账号和随机密码通过运行目录内权限为 0600 的 `app.env` 本机取用。仿真工作台的隔离标识出现后，即可选场景、配置车队、保存配置并开始。

- **车队设置**填写线路、方向、初始站、数量、座位、初始载客、发车间隔、站间行驶与停站时间。站间时间为 0 时使用线路站序记录。固定班次按出发间隔运行，车辆到终点后换向再运行一趟。
- **真人乘客**从本机乘客页注册，选择去程或返程，再选起点和同方向下游目的站。可以搭乘自动车或人工车辆。
- **真人司机**将车组的人工车辆数设为大于 0，运营模式选混合。管理员在车辆详情中查看该辆仿真车的临时司机账号，再在司机端登录。沿这一趟的站序上报到站、下客、上客和离站。人工车当前位置采用最近一次到站上报，区间进度和预计到站时间适用于自动运行的车辆。人工车的车载预测依赖下游目的站与当前候车。
- **运营干预**在车辆详情中执行故障、退出和复运。选中正在行驶的车辆执行故障时会冻结当前运行安排。故障或退出后，车上乘客继续保留车次关联，复运后可继续到达目的站。
- **历史与复盘**选择历史运行以及线路方向和行程，可拖动进度或播放，导出运行配置、随机种子、乘客记录、车辆事件、逐站数据和任务生命周期。停止会取消本轮尚未上车的请求并撤下仿真车队。重置清理当前工作台视图，历史与实验原始数据仍可查看。运行目录的 `operation/` 保存该隔离实例的配置和档案。

关闭隔离进程使用 `python3 simulation/runtime.py stop --run-dir /private/tmp/shuttleflow-demo-20261118`。保留历史与日志，并删除临时环境凭据。关闭后需新开运行目录开展新实验。

## 业务与实验口径

- 乘客登记、身份、签到、取消、司机创建和司机上报走 ShuttleFlow 认证及业务接口。签到请求存储起终点，真实上客事件关联车辆和行程，每次单向运行使用独立行程号。自动乘客按目的站下车，初始载客为无乘客身份的场景参数，于终点清空。
- 拓扑用既有线路站序和 `distance_m`。位置和到站预计根据离站时刻、站间时间与停站时间推算。实际人数及逐站上下客来自提交后的事件，预测曲线与实际离站载客分别标识。
- 固定班次使用全车队执行班次。简单阈值采用 15 人触发既有任务派车，智能策略加入分级阈值、Java CUSUM 和任务综合评分。两种需派车的策略均保留基础班车并使用备车。课表查询与调度触发读取模拟时钟，课表预置仍为单独的待调度建议。
- 智能策略比较基于同一随机种子与客流计划。近期历史会按相同配置归组，切换策略并重新运行即可记录对照。CP-SAT/启发式多车建议、Python Kalman、消融和 Python 预测仍在高级实验区。
- 各角色的页面从各自权限的视图读取数据，收到现有 WebSocket 的仿真更新提示后按角色刷新。乘客只看到路线、排队和车辆概况，司机可看到绑定车辆及上下客预测，管理员可读行程历史与任务原因。

## 自动验收

```bash
bash simulation/acceptance_operation.sh
```

脚本用项目锁定的 Playwright 和独立无头 Chromium，生成报告、截图和原始 JSON 至 `output/operation-v13/`。每次执行创建一个新库，脚本退出时清理相关进程。此前的离散基线 HTTP 测试仍可用 `bash simulation/acceptance_local.sh`。
