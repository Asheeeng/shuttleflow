## 2. 正式切换阻断：仿真记录和真实记录未隔离

源码依据：[`simulation/operation.py`](../../simulation/operation.py) 的 `setup`、`recover_interrupted`、`cleanup` 和 [`OperationController.java`](../../backend/src/main/java/com/gzu/shuttle/controller/OperationController.java) 的 `clearWaiting`、`ledger`、`cursors`。仿真启动记录请求、预警与任务的最大 ID；清理按 ID 下限查找记录，未按仿真批次或专用数据隔离。同期创建的正常候车单可能被取消，也可能把同期正常预警和调度任务纳入清理。仿真时钟、策略及检测状态有进程级影响，单给候车单加标记仍不能隔离所有风险。

**本地实际复现**：在独立 MySQL 库、独立 Redis 的环境中，运行 [`simulation/operation_lifecycle_check.py`](../../simulation/operation_lifecycle_check.py)。仿真出现红色运力预警后，一个经普通注册和签到接口创建的乘客加入队列；管理员停止仿真后，实时站点队列归零，普通乘客再主动取消时收到业务码 409。现有用例把能够清理仿真期间加入的人类测试乘客视为实验环境的预期行为；同样的行为在正式入口属于上线阻断。未对 VPS 或正式数据库执行此测试。

可恢复、改动范围较小的方案：

1. 正式 V1.3 使用新的业务 schema 与独立数据库账号；可复用本机 `3308` MySQL 实例。先使用校验通过的 V1.2 备份离线演练数据迁移，对关键表、账号、车站线路、待办及状态逐项核对。切换前关闭正式环境中的运营仿真和算法实验开关，开启正式 CUSUM 调度；正式 Java 使用自己的 Redis/AI 状态和会话配置。已有模拟 schema 继续保留，Navicat 配置不动。
2. 实验环境沿用旧模拟数据，使用独立 Java/AI 进程、Redis 状态、会话及业务凭据。资源不足时按需启动实验。两个指定域名统一指向正式实例时，实验控制另走受保护入口（如 SSH 隧道），不得共用正式实例或以公开路径代理内部服务。
3. 正式入口去掉公共 Basic Auth 前，除 Java 的角色/车辆归属/CSRF 验证外，在 Nginx 拒绝 `/api/admin/operation/`、`/api/operation/` 等实验路由，不代理 AI 和控制进程；覆盖传入的代理头、去除 `Forwarded`、`Authorization` 及内部认证头。对两个 HTTPS Origin（含 WebSocket）做精确配置，使用 host-only、Secure、HttpOnly 会话 Cookie；两个域名应能独立登录，不扩大 Cookie 域。逐接口验证匿名、乘客、司机、调度员与管理员权限，不把现有 Basic Auth 当成唯一屏障。V1.3 仓库中的代理模板已清除内部请求头，线上生效配置仍需 root 复核。
4. 让独立实验启动、停止、重置和异常退出，验证正式端的用户、候车单、预警、任务和时钟不变；再完成两域名新浏览器注册、三端闭环、空闲 WSS、Navicat TLS 和备份监控验收。均通过后方能切换正式流量和停 V1.2。不要根据已有实验数据或本地单项通过来下线旧服务。

## 4. VPS 备份、Fail2ban 和回滚

脚本已经上传到 `/home/shuttle/vps-deploy/preflight-production-cutover.sh`，并在本地及 VPS 执行 Bash 语法检查；**脚本主体尚未以 sudo 执行**。放在已有 Tabby 的 SSH 会话执行：

```bash
sudo bash /home/shuttle/vps-deploy/preflight-production-cutover.sh "$SSH_CONNECTION"
```

脚本先核对发布目录、配置、实例及 Navicat 授权；备份两套 SQL、发布目录、环境、Nginx/systemd 配置，验证压缩和 SHA-256；用独立临时 MySQL socket 载入两份 SQL，正式 MySQL 实例不参与恢复。归档包含私密配置和 TLS 文件，保存在 VPS 的 root-only 目录，不能上传 Git。若资源不足、备份或恢复失败则退出，保留已有输出和诊断；归档时须保持不进行其他部署。完整性校验与临时恢复只有脚本实际通过后才成立，异地备份尚未验证。

备份后检查 journal 中确有公钥登录记录，再为 `sshd` jail 配置 systemd 后端，将当前可信 SSH 来源加入保留列表，先测试配置再恢复 Fail2ban。只新增专用 `.local` 文件；不更改 SSH、UFW、安全组或 Nginx，失败时脚本撤回专用配置。原终端应保持连接，另开新的 SSH 会话验证登录。如果运行后出现异常，在原终端将专用 `/etc/fail2ban/jail.d/99-shuttle-sshd-journal.local` 移出加载目录，再按原状态恢复 Fail2ban；禁止为了验证而触发实际封禁。

**未来域名切换的回滚约束**：将实际 Nginx vhost、V1.2 发布路径和服务记录在备份清单；若切流量后需回退，先停止正式 V1.3 上继续接收写入，保留并核对切换后新增的数据，按备份配置恢复原代理，通过 `nginx -t` 后 reload，并验证旧版 readiness、HTTPS 与 WSS。没有验证写入同步前不能盲目切回旧数据库，也不能将旧转储覆盖新数据。V1.2 仅在完整验收后可停止，旧文件、库和备份继续保留；还须先确认所有下线单元都不被正式 V1.3 与监控/备份依赖。本次尚未切换，无需执行此回滚。
