## 验收结论

V1.2 已部署并在香港 VPS 本机健康运行。Spring Boot、FastAPI、MySQL、Redis、Nginx、cron 均为 systemd active/enabled。HTTP 业务端口只绑定回环地址；没有域名和可信 HTTPS 证书，因此 Nginx 保留默认页，没有将登录或业务页面公开到明文 HTTP。

## 部署步骤与实际结果

- SSH 使用已验证的主机指纹和 `shuttle` 用户密钥登录。有效SSH设置为22端口、公钥认证开启、密码认证和root远程登录关闭。UFW预检通过，脚本没有更改SSH、UFW或云安全组。
- 远端分支部署前核对仍指向提交 `5a975732…`，`main` 仍为 V1.1。应用发布目录 `current` 的代码SHA为目标提交；未部署后续文档/脚本修改，也未合并或覆盖 `main`。
- 用 MySQL 官方 APT 仓库安装8.0.46，配置 `bind-address=127.0.0.1`、`require_secure_transport=ON`。新服务器无既有业务数据库；经确认后初始化全新 `shuttle_db`。迁移脚本未运行，因为没有旧库需要迁移。
- 应用通过 `shuttle_app` 最小权限账号连接；另有独立备份和监控账号。MySQL root 使用本机Unix socket管理，不供应用连接。Redis配置了随机认证口令，凭据放在root-only环境文件。
- 服务器侧从确认的目标分支构建Java包，安装AI Python虚拟环境及systemd单元。第一次启动发现发布树受 `umask 077` 影响，服务用户无法遍历；已将隔离发布树权限修正为root所有、`shuttleflow`组只读/执行，并复跑健康检查。新装脚本也加入了权限修正和健康等待。
- 正式管理员由隐藏终端输入的一次性引导密码创建；引导变量随后从环境文件移除。没有在本报告记录密码、令牌或数据库口令。

## 后续维护命令

在Tabby通过SSH登录后执行。更新必须显式指定V1.2分支，脚本不会自动迁移数据库：

```bash
sudo systemctl status shuttleflow shuttle-ai mysql redis-server
sudo journalctl -u shuttleflow -u shuttle-ai -n 100 --no-pager
sudo bash /opt/shuttleflow/current/deploy/bin/health-check.sh
sudo bash /opt/shuttleflow/current/deploy/bin/monitor.sh
sudo bash /opt/shuttleflow/current/deploy/bin/backup-mysql.sh
sudo env SHUTTLE_INSTALL_DIR=/opt/shuttleflow \
  SHUTTLE_DEPLOY_BRANCH=codex/v1.2-hardening-passenger-auth \
  bash /opt/shuttleflow/current/deploy/bin/update.sh
sudo env SHUTTLE_INSTALL_DIR=/opt/shuttleflow \
  SHUTTLE_ROLLBACK_COMMIT=<本机已保留的旧发布SHA> \
  bash /opt/shuttleflow/current/deploy/bin/rollback.sh
```

数据库恢复只能使用 `restore-mysql-to-new-db.sh` 恢复到新的 `shuttle_restore_*` 库；不要将初始化脚本用于已有库。
